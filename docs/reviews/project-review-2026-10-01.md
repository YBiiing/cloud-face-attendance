# 人脸签到系统前后端代码审查报告

审查日期：2026-10-01。基线：`3df679ab992a5949a8c83ca9de675f7b8dd6e1b5`。

## 1. 结论与范围

本轮确认 **6 项问题：2 项 P1、4 项 P2**，涉及上传事务与文件一致性、共享队列容量、API 事件循环和前端任务恢复。建议先修复数据一致性和队列边界，再处理阻塞调用与页面恢复。本报告是审查结果，所列问题尚未修复。

由一个审查子智能体检查项目，另一个报告子智能体回查关键代码、去重并整理报告。审查对象包括：

| 层次 | 检查范围 |
| --- | --- |
| 前端 | 7 个 HTML 页面及全部 9 个页面/公共 JS 模块；注册、登录退出、照片管理、场次、签到、记录、请求封装与任务轮询 |
| 后端 | 注册/重试、认证与 CSRF、照片权限、班级场次、匿名签到、任务查询、记录查询；同步数据库访问、事务与文件处理 |
| 识别与任务 | 模型调用、全库检索、名单校验、特征版本、执行尝试、补投恢复、队列配额 |
| 运维辅助 | Compose 服务关系、备份恢复和文件清理；历史验证记录与当前验收边界 |

本轮没有修改业务代码、运行数据库测试、操作开发数据库或停止服务。工作区原有 `docs/api-contract.md` 修改不属于本轮改动，保持原样。本轮只新增此报告。

优先级含义：P1 为应优先解决的数据一致性或服务容量保护问题；P2 为有明确触发条件的并发/功能问题。静态确认指代码中存在可达失败路径，不代表该故障已经在真实数据库或手机上复现。

## 2. 问题清单

### R1 · P1 · COMMIT 结果不确定时删除照片，可能破坏已提交任务

**定位**：`app/api/registration.py:50,60,88,92`；`app/api/faces.py:64,72`；`app/api/checkins.py:40,48-49`。同类路径见 `scripts/backup_data.py:122-140`。

**证据与触发条件**：上传接口均在 `session.commit()` 正常返回后才设置 `retained=True`；`finally` 在该标记为假时删除上传照片。如果 MySQL 已完成提交，但提交响应因连接中断未到达客户端，`commit()` 会抛异常，标记仍为假。此时数据库可能已经持有 PENDING 任务和图片路径，接口却删除了文件。签到接口还会释放该任务的容量预留。

隔离恢复工具也在事务上下文退出异常时无条件删除所有新写入照片；若异常发生于已成功提交但响应丢失，同样可能留下有记录、无照片的恢复库。该工具限制在空测试库，因此此处影响范围是隔离恢复环境。

**影响**：补投恢复只能重新找到任务，不能恢复已删除的原图；任务随后可能变成 PROCESSING_FAILED，数据库与文件不一致。恢复工具可能生成不完整的恢复结果。

**建议**：区分“确认未提交”和“提交结果未知”。提交结果未知时保留文件，通过新连接核对任务/恢复结果；数据库暂不可访问时，交给已有带保留期和引用校验的孤儿清理机制处理。容量预留也应保守保留或进行持久化校正。不要仅因捕获 OperationalError 就假定事务已回滚。

**建议验证**：模拟提交已生效而客户端抛错，断言数据库任务引用的照片仍在；再验证提交确实失败时孤儿文件最终可清理。恢复工具使用独立目标验证相同边界。

**本轮证据等级**：静态调用链确认；未执行真实 MySQL 提交响应丢失实验。

### R2 · P1 · 注册与照片任务绕过共享推理队列的容量限制

**定位**：`app/api/checkins.py:39`；`app/services/capacity.py:6`；`app/api/registration.py:48-51,87-88`；`app/api/faces.py:63-64`；`app/services/tasks.py:53-59`；`app/jobs/worker.py:51-57,76-79`。

**证据与触发条件**：签到在创建任务时调用 `reserve()`，注册、注册重试和照片新增/替换没有此调用。它们最终都使用同一个 `attendance.process` Celery 任务入口和共享 worker；终态释放逻辑也只处理 CHECKIN。注册每 IP 每分钟 10 次、照片上传每 IP 每分钟 20 次的限流确实存在，但它们不统计正在等待或执行的任务，不能代替全局待处理容量。

**影响**：多个来源持续注册或上传照片，或者 worker 暂停时继续接收请求，会在签到配额之外增加任务和图片。签到看到的“50 个配额”不能约束共享推理服务的总积压，已接收签到也可能被这些任务拖延至超时。

**建议**：让所有昂贵识别任务共用总容量，或分别设置有上限的任务配额并提供明确的队列隔离/调度规则；同步更新完成、失败、超时和提交异常路径的释放/校正机制。保留现有 IP 限流作为另一层保护。

**建议验证**：先用 ENROLL/FACE 填满可用容量，再提交 CHECKIN，确认系统拒绝超额接收或遵守明确保留给签到的容量；验证终态和过期预留可回收。测试应在隔离服务中进行。

**本轮证据等级**：静态入口、投递与 worker 路径确认；未运行混合任务饱和压测，不据此给出吞吐数字。

### R3 · P2 · 异步上传路由直接执行同步数据库和消息调用

**定位**：`app/api/checkins.py:18,32,39-40`；`app/api/registration.py:29,40,50-51,64`；`app/api/faces.py:42,58,64`；`app/database.py:31-40`；`app/services/tasks.py:53-59`。

**证据与触发条件**：路由是 `async def`，但内部直接调用同步 SQLAlchemy Session、PyMySQL、Redis 和 `celery_app.send_task()`。密码哈希已使用线程池，数据库事务和消息调用尚未采用同类隔离。发生行锁竞争、连接池等待、数据库或 Redis 网络变慢时，这些调用在当前 API 事件循环中等待。

**影响**：同一 API 进程内其他请求的调度也被延迟；即使模型已交给 Celery，接收请求阶段仍可能成为并发瓶颈，并拖慢任务轮询和页面请求。

**建议**：保留异步请求读取，将完整同步事务服务及同步外部调用放进受控线程池；在该同步服务内部创建、使用并关闭 Session，避免同一 Session 被多个线程并行使用。也可整体改用异步驱动，但没有必要仅为修复本问题引入大范围架构变化。

**建议验证**：在隔离测试里人为延迟数据库锁/消息投递，同时请求一个无关的轻量接口，验证后者不随前者同步阻塞；测量后再报告实际改善。

**本轮证据等级**：静态执行链确认；未测量真实阻塞时长或性能提升。

### R4 · P2 · 浏览器历史缓存恢复后，注册与照片页继续使用已取消的控制器

**定位**：`web/assets/register.js:4,25,44-45`；`web/assets/faces.js:4,41-45`；`web/assets/api.js:6-11`；`web/assets/tasks.js:12,23`。已有相邻实现可参考 `web/assets/checkin.js:56-57`。

**证据与触发条件**：注册和照片页在 `pagehide` 时调用 `controller.abort()`，没有在 `pageshow` 的历史缓存恢复分支重新加载或重建控制器。当浏览器将文档从 BFCache 恢复时，旧的 aborted signal 仍被使用。

**影响**：注册提交立即取消，且错误被 `if (!controller.signal.aborted)` 隐藏，页面可能一直显示“正在上传”。照片页的上传请求没有传入该 signal，仍可能被后端接收，但后续轮询立即终止，页面无法正常展示该次结果。

**建议**：采用与签到页一致的历史缓存恢复策略，或明确重建控制器并恢复待处理任务。确保不会为获取结果而重传已经接收的业务请求。

**建议验证**：注册和照片管理分别覆盖离开页面后返回、上传前返回、任务处理中返回；检查请求是否重复、轮询是否恢复及提示是否准确。

**本轮证据等级**：审查子智能体在隔离 Edge 页面、全部 API mock 条件下模拟 `pagehide/pageshow(persisted)`，注册提交观察到 POST 为 0，按钮可点击但提示停留在上传状态。该实验验证事件恢复路径，不等于真实手机或所有浏览器实际命中 BFCache 的验收；照片页结论为静态回查。

### R5 · P2 · 照片任务失败后原样重试，一直命中原失败任务

**定位**：`web/assets/faces.js:5-8,41-45`；`app/api/faces.py:57-60`；`app/services/tasks.py:33-37`。

**证据与触发条件**：照片页在收到 FAILED/REJECTED 终态后恢复表单，却没有更新幂等键；键仅在输入变化、切换替换目标或成功后取消替换等情况下更新。用户看到 PROCESSING_FAILED 或 TASK_TIMEOUT 后，保留同一张照片直接再次提交，后端 `find_replay()` 正确返回旧任务，而不是创建新的尝试。

**影响**：界面允许“重试”，实际上重复查询同一个终态失败任务。即使服务已恢复，用户也不能通过原样重试重新处理该照片。

**建议**：明确区分“请求结果未知，需要用原键找回”和“已确认终态失败，用户主动重新尝试”。仅在后者生成新键；网络错误或尚未确认接收状态时继续保留旧键。

**建议验证**：第一次返回 FAILED，用户不重新选图直接重试，断言生成新请求键并创建新任务；同时覆盖丢失响应场景仍使用原键且只生成一个任务。

**本轮证据等级**：前后端幂等调用链静态确认；未执行真实失败任务的数据库重试实验。

### R6 · P2 · 失效任务凭证导致注册与签到页持续锁定

**定位**：`web/assets/register.js:22-26,31-38,46`；`web/assets/checkin.js:14,30-33,39-45,60-65`；`web/assets/tasks.js:17-19`；`app/api/tasks.py:15-22`。

**证据与触发条件**：sessionStorage 中的任务 ID/凭证格式正常，但目标任务不存在或凭证无效时，服务返回 404。两个页面都在轮询前设置 pending 并保存凭证，只在正常取得终态时清除 pending。轮询抛出 404 后，表单仍因 pending 被禁用，保存的数据也没有清除；刷新页面重新进入同一路径，“继续查询”仍然返回 404。

**影响**：使用了旧环境浏览器状态、任务被管理性清除或凭证内容失效时，用户无法通过页面完成新的注册/签到，需要手动清理浏览器存储。当前浏览器注册测试将第一次 404、第二次正常结果作为临时中断，未覆盖持续 404 的退出路径。

**建议**：将不可恢复的“任务不存在/凭证失效”与可重试的网络/503错误分开处理，退出失效 pending，提供清晰的重新开始或联系管理员入口。注册时若账户已存在，不能假定清空任务凭证就能重新注册，应提示恢复账户录入的可用方式。对于结果未知的临时失败，继续保留原任务与幂等信息。

**建议验证**：分别为注册页和签到页注入持续 404，验证刷新、再次查询和重新开始可退出死循环；保留网络中断后的原任务恢复测试。

**本轮证据等级**：后端错误含义及两个页面状态机静态确认；未将此项声称为本轮浏览器复现。

## 4. 建议修复顺序

1. **R1：提交不确定性与照片保留。** 先保护数据库引用的文件，再覆盖四个上传入口和隔离恢复工具的失败边界。
2. **R2：所有识别任务的容量管理。** 定义全局总容量或各类任务预算，完成接收、结束、超时和异常校正的闭环。
3. **R3：隔离同步 I/O。** 将事务和消息调用移出事件循环，并测试锁竞争时轻量接口仍可响应。
4. **R4、R5、R6：统一前端任务恢复语义。** 分别处理历史缓存恢复、已确认失败后的新尝试、凭证失效与临时网络中断，避免改一种重试而破坏另一种幂等保护。
5. **执行针对性回归后补全真人和实机验收。** 优先验证上述触发条件，再运行受影响的现有集成与浏览器测试；不以扩大功能范围替代修复。

每项可独立提交，但此报告不执行修复、Git 提交或推送。
