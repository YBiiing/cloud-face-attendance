业务规则沿用 `docs/design.md` 中的班级场次方案。执行安排以本计划为准：由个人完成，本地功能与验证优先，云服务器、Nginx、公网 IP、正式 HTTPS 和云端压测最后处理。提交文档中的团队名单不作为开发分工。

本轮目标是本机与同一可信局域网内的手机可完成注册、照片库管理、创建课程签到、匿名签到和记录查询。目标数据库始终为 MySQL，不以 SQLite 测试结果代替 MySQL 的事务与并发验证。GPU、Faiss、活体检测、多机扩容、短信、找回密码和原生 App 不在本轮范围。

## 2 固定的业务与技术约定

### 2.1 业务规则

1. 注册包含姓名、学号、班级、密码和标准照。账户与有效人脸都建立成功后，才激活账户；公开注册不能指定管理员角色。
2. 注册上传标准照、场次签到上传照片均无需登录；维护标准照片库和查询历史记录需要登录。普通用户只能访问自己的资源，管理员管理班级、场次及全体记录。
3. 先完成班级人员注册，再由管理员选择一个班级并创建场次。创建时冻结该班级已注册且有效的人员名单；已发布的名单、班级和起止时间不编辑，仅支持提前结束。
4. 公开签到页通过随机场次码定位场次。上传不包含目标 user_id、学号或设备身份；服务器先在全体有效人脸中识别人，再核对场次名单。
5. 每人每场次只成功一次；同一天不同场次分别记账。未知人员、身份不明确或不属于名单的人员都不能写入成功记录。
6. `received_at` 是服务器完整接收文件并通过基础文件校验后记录的时间。资格区间为 `[starts_at, effective_end)`；没有提前结束时 effective_end 为 ends_at，否则取 ends_at 与 closed_at 的较早者。
7. 截止前接收的任务允许截止后完成识别。截止后新请求拒绝；重复请求若是同一已接收任务，应返回原任务，不重新计算接收时间。客户端时间不参与资格判定。
8. 场次统计的应到数来自冻结名单，已到数来自成功记录；差集为未签到。截止后仍有有效待处理任务时显示“结果处理中”，不提前把统计视为最终结果。
9. 签到照片不会自动加入标准照片库。模型版本、预处理版本和向量格式一致的特征才能比较。

### 2.2 本地运行环境

采用 Windows 编辑源码、Docker Desktop Linux 容器运行服务的方式。本地 Python 版本不直接决定容器中的依赖；容器首轮以 Python 3.11 为拟定基线，完成模型安装试跑后锁定实际可用的小版本和依赖。版本试跑失败时记录具体依赖原因，再做最小调整。

| 服务 | 本地安排 | 边界 |
| --- | --- | --- |
| api | FastAPI 与 Uvicorn，提供 H5 页面及 /api | 默认仅映射 127.0.0.1:8000；手机联调阶段再使用专门的局域网配置 |
| mysql | 独立 MySQL 8.4 实例和命名数据卷 | 开发工具通过 127.0.0.1:3307 连接；容器间使用 mysql:3306 |
| redis | 为任务投递、限流和配额服务 | 默认不向宿主机发布端口；不作为签到记录的唯一存储 |
| worker | 与 api 使用同一应用镜像，独立执行人脸任务 | 从 1 个推理进程起步，再根据测量调节 |
| scheduler | 定时补投、任务恢复与文件清理 | P3 引入基础恢复，P6 验证进程故障与清理完整性 |

API、worker 和 scheduler 使用同一照片数据卷；模型使用单独持久化目录。模型文件、照片、特征、数据库文件、密码和 `.env` 不提交到 Git。现有宿主机 MySQL 实例不修改、不升级、不用其原有数据库做测试。

本地开发的普通 HTTP 使用非 Secure 的开发会话 Cookie，但仍启用 HttpOnly、SameSite 和授权校验；该设置仅限显式 local 配置。后续公网配置必须要求 HTTPS 和 Secure Cookie。手机拍照先用文件控件，不依赖 HTTP 局域网下的实时相机预览。

## 5 P2 人脸模型与图片处理

### P2-01 安装和加载真实模型

- **状态与依赖**：已完成；依赖 P1-02。验证见 `docs/verification/p2-01.md`。
- **开发内容**：在目标 Linux 镜像内验证 OpenCV、InsightFace、NumPy 和 CPU ONNX Runtime 的兼容组合；预下载 buffalo_l 所需检测、识别权重。记录来源、文件校验值、许可与实际依赖版本，再生成锁文件。
- **运行约定**：模型在 worker 进程启动后加载并预热，不放在每次 HTTP 请求内，也不依赖首个用户上传时联网下载；多个进程各持有自己的模型实例，不把已建立的推理 Session 随意跨进程复用。
- **产出位置**：`app/face/engine.py`、`scripts/check_model.py`、`requirements.lock`、模型配置说明；权重留在忽略目录/数据卷。
- **验收**：脚本能报告检测和识别模型加载成功、实际执行 provider、模型版本与耗时；阻断外网后仍可加载已有权重；权重缺失时明确失败，不切换到假识别。

### P2-02 图片接收与基础校验

- **状态与依赖**：已完成；依赖 P1-01、P1-02。验证见 `docs/verification/p2-02.md`。
- **开发内容**：流式限制上传大小，核对真实文件格式、解码结果与像素上限，处理照片旋转方向；统一转换到模型所需色彩格式。存储文件名由服务器生成，不使用客户端路径；上传失败只清理本次新文件。
- **输入范围**：初版接受 JPEG/PNG，其他格式明确提示转换或重拍；手机 HEIC 等格式不假定支持。上传字节上限、像素上限写入配置，前端提示与后端限制保持一致。
- **产出位置**：`app/services/uploads.py`、`app/face/images.py`、`tests/integration/test_uploads.py`。
- **验收**：正常照片、旋转照片、损坏文件、伪装扩展名、超限文件、零字节文件、路径穿越文件名均有确定结果；被拒绝文件不进入模型，也不残留可访问原图。

### P2-03 人脸检测与特征提取

- **状态与依赖**：代码与基础验证完成，真实人脸样本验收待补；依赖 P2-01、P2-02。见 `docs/verification/p2-03.md`。
- **开发内容**：定义 `extract(image) -> embedding + quality + model_version` 适配接口；检测人脸数量，要求恰好一张，检查最小脸尺寸与基础清晰度，按关键点对齐并提取向量。检查向量维度、有限值和范数，统一 L2 归一化。
- **错误语义**：区分 NO_FACE、MULTIPLE_FACES、LOW_QUALITY、INVALID_IMAGE 与 MODEL_UNAVAILABLE。模型故障属于系统失败，不能显示为“未录入人员”。注册与签到共用同一预处理链。
- **产出位置**：`app/face/engine.py`、`app/face/types.py`、提取脚本和对应输入校验测试。
- **验收**：真实模型对可用人脸返回合法向量；无人脸/多脸样本返回对应拒绝码；重复加载已缓存模型不会在每个请求重新下载或初始化。阶段报告不保存原始向量。

### P2-04 按人员检索与拒识规则

- **状态与依赖**：已完成规则实现与确定性验证；依赖 P2-03。见 `docs/verification/p2-04.md`。
- **开发内容**：实现归一化向量点积比较，先按 user_id 汇总每人的最高分，再比较不同人员的前两名；使用相似度阈值和分差阈值判断。避免同一人的两张标准照被当成“两个相近人员”。
- **边界**：空库返回未识别；仅一位候选人员时只应用绝对阈值；向量版本不一致时拒绝混算；分差不足返回身份不明确。接口只返回匹配结论和内部必要分数，不泄露全库候选名单。
- **产出位置**：`app/face/matcher.py`、`tests/unit/test_matcher.py`。
- **验收**：用确定性向量验证按人员聚合、空库、单人、多照、同分、阈值上下边界和版本不一致；这些测试只证明算法逻辑，不能替代真实模型准确率试验。

### P2-05 真实样本与阈值试验

- **状态与依赖**：未开始；依赖 P2-03、P2-04，以及经本人同意的照片。
- **开发内容**：准备已录入人员的标准照与不同时间拍摄的测试照，再准备真正未录入人员照片；覆盖适度角度、光线变化及模糊等情况。调参集与最终验收集分开，不拿同一张标准照反复验证自己。
- **记录方式**：记录样本人数、照片数、正确接受/错误接受/错误拒绝/不明确次数、单张耗时和测试硬件。阈值落入配置并保留试验依据；没有样本时标注待验证，不编造准确率。
- **产出位置**：`scripts/evaluate_faces.py`、`docs/verification/model-baseline.md`；私有照片和逐人分数表留在忽略目录。
- **验收**：已知和未知两类场景均有真实测试结果；观察到错误接受时继续调试或更换基线，不为了演示只保留容易通过的照片。性能不够时先测瓶颈，再决定是否用轻量模型。

**P2 阶段交付**：可复用的真实人脸处理模块、可配置拒识策略和效果报告。样本缺失时只能标记运行链路完成，效果验收仍待完成。

## 6 P3 注册登录与照片库

## 9 P6 本地联调与可靠性验证

### P6-01 队列容量与故障恢复

- **状态与依赖**：未开始；依赖 P3-02、P5。
- **开发内容**：完善待处理任务容量、上传限流、排队/执行超时、有限重试及 worker 心跳。入队配额采用 Redis 原子预留并与请求关联，数据库失败释放预留；对进程崩溃和过期预留设计校正，不能用“读队列长度再入队”当作严格容量控制。
- **恢复规则**：数据库作为任务状态依据；PENDING 任务可补投；RUNNING 的执行租约过期后，在重试上限与截止条件内重新认领，否则转 FAILED。尝试标识必须阻止旧进程晚到结果覆盖新状态。任务确认、进程丢失重投和预取策略在 Linux worker 中实际验证，不仅依赖 Celery 默认值。
- **产出位置**：`app/jobs/recovery.py`、队列配置、`tests/integration/test_job_recovery.py`。
- **验收**：分别在数据库提交后投递前、认领后、推理后写入前、事务提交后模拟 worker/Redis 中断；恢复后无永久处理中任务、重复记录或假成功。相同缺陷复测通过后停止扩展无关故障场景。

- **数据保护**：仅清理本项目存储目录内由任务管理的文件，不能根据用户提交的路径删除文件；活动任务引用的文件不删除。备份 MySQL 与标准照，在独立测试数据卷验证恢复后特征可读取。
- **产出位置**：文件清理/恢复工具、`tests/integration/test_concurrency.py`、`test_storage_lifecycle.py`。
- **验收**：识别期间删除/替换照片不会接受失效特征；关闭场次并发上传遵守 received_at；超时任务不能复活；运行清理后有效照片和测试外文件完整。

### P6-03 分层压测与参数调整

- **状态与依赖**：未开始；依赖 P6-01、P6-02，以及可用真实样本。
- **开发内容**：先用模型替身测试接口、队列、去重和数据库竞争，再用真实模型测完整流程。并发按 1、5、10、20 逐档执行，每档记录持续时间、请求数、照片大小、人员库规模、模型与机器配置、worker 数和推理线程数。
- **指标**：分别记录接收耗时、排队耗时、推理耗时、端到端 P50/P95、成功完成吞吐量、拒识率、基础设施失败率和资源占用。202 不计为处理完成；相同幂等键命中、同人重复签到、不同人员新签到分组报告。
- **调整原则**：接近资源上限或出现持续积压时停止加压；根据瓶颈调节 worker/模型线程数、队列上限与超时，避免进程数乘线程数导致 CPU 争抢。分开报告队列容量与实际处理能力。
- **产出位置**：`scripts/load_test.py`、`docs/verification/local-load.md`。
- **验收**：给出本机测得的可用区间与限制，不预先承诺并发数字；业务去重/时间规则在压力下仍成立，资源恢复后服务能继续接受请求。云端容量最后另测。

### P6-04 手机实机与浏览器验收

- **状态与依赖**：未开始；依赖 P5-05、P6-01。
- **开发内容**：增加显式局域网启动配置，仅对可信局域网开放 API 页面；MySQL/Redis 保持内部或宿主机回环绑定。手机与电脑同网，通过电脑局域网 IP 打开场次链接；如果需要防火墙规则，仅针对项目端口和专用网络配置，并记录回退方法。
- **浏览器测试**：验证拍照或选图、旋转方向、前后台切换、页面刷新、弱网重试、登录退出与会话 Cookie。遇到 HEIC 不支持时明确提示，不把浏览器兼容性问题当模型拒识。实时摄像头预览不作为 HTTP 本地验收前提。
- **产出位置**：局域网配置、`docs/verification/mobile-local.md`、移动端缺陷修复。
- **验收**：至少一台实际演示手机完成无登录签到和登录后查记录；记录机型、系统、浏览器与网络方式。只有电脑浏览器结果时标明手机未验证。

### P6-05 单人运行手册与本地交付

- **状态与依赖**：未开始；依赖 P1 至 P5 及 P6-01 至 P6-04 的相应验证通过。
- **开发内容**：整理从干净目录复制配置、构建、迁移、准备模型、初始化管理员、创建班级、启动服务到完整演示的步骤。说明常用日志查询、停止服务、数据备份、任务失败定位及测试命令；更新任务完成记录。
- **环境复现**：用独立 Compose 项目和全新测试数据卷验证冷启动说明；复现不复用主开发库已有账户、隐含环境变量或未写明的模型文件。保留必要模型缓存并在文档中写清获取方式，不误删用户数据。
- **产出位置**：`README.md`、`docs/local-runbook.md`、`.env.example`、验证报告索引。
- **验收**：按手册能从零启动并重做核心演示；重启后有效数据保留；最终报告区分已实现、已验证、待照片/手机验证和最后才进行的云部署事项。Git 提交或推送另按用户明确指令执行。

**P6 阶段交付**：个人可复现运行的完整本地系统、真实功能证据、并发与恢复报告。公网 IP/HTTPS/云资源验证仍未执行，不将本地验收描述为课程云端验收全部完成。

## 10 数据库增量与前端页面对照

### 10.1 迁移顺序

| 迁移阶段 | 表与约束 | 关键验证 |
| --- | --- | --- |
| P1 | classes、users；学号唯一与班级外键 | 空库升级、重复学号、事务回滚 |
| P3 | login_sessions、face_samples、face_library_state、recognition_tasks | 会话撤销、录入原子性、特征版本、幂等键唯一性 |
| P4 | attendance_sessions、session_members | 场次码唯一、名单联合主键、创建快照 |
| P5 | attendance_records；任务场次外键与接收时间 | UNIQUE(session_id, user_id)、名单外键、不同场次隔离 |
| P6 | 必要索引和恢复字段的增量迁移 | 保留现有记录、超时恢复、并发查询 |

字段细化时至少覆盖：任务的业务归属、执行尝试、重试次数、创建/接收/截止/完成时间、错误码；会话的令牌哈希、CSRF 校验信息和过期时间；标准照的路径、向量维度/类型、模型与预处理版本。数据表仅保存实现所需状态，不保存可由场次时间直接计算的重复状态。

### 10.2 页面完成顺序

| 页面 | 先实现的交互 | 必须接入的真实能力 |
| --- | --- | --- |
| 首页 | 注册、登录、场次入口说明 | 服务状态，不展示虚构统计 |
| 注册与登录 | 班级选择、照片预览、任务状态 | 真 MySQL、真实人脸录入、会话 |
| 照片库 | 查看、新增、替换、删除 | 资源权限、受保护原图、特征更新 |
| 场次管理 | 选班级、设时间、复制链接、关闭 | 冻结名单、服务器时间规则 |
| 场次签到 | 公开场次信息、拍照、重试、反馈 | 匿名任务、真实检索、名单校验 |
| 签到记录 | 场次筛选、个人/管理员视图、分页 | 数据库记录、应到/已到/未到统计 |

## 11 测试执行与证据规范

以下是后续拟提供的命令形态，当前尚无对应配置或代码，不能直接视为已执行结果。所有命令在 PowerShell 中从仓库根目录运行；实际脚本建成后以运行手册中验证过的命令为准。

```powershell
docker compose config --quiet
docker compose up -d mysql redis
docker compose run --rm api alembic upgrade head
docker compose run --rm api python -m scripts.check_model
docker compose run --rm api python -m scripts.create_admin
docker compose up -d api worker scheduler
docker compose -p face-attendance-test -f compose.yaml -f compose.test.yaml run --rm tests pytest -q
```

测试 Compose 必须重定义数据库、照片和模型测试路径，使用独立项目名和卷；不能把清理脚本指向开发资料。停服务默认保留数据卷，手册不把删除数据卷的命令列为日常停止方式。模型准备可能需下载大文件，失败需说明网络或依赖原因，不写成识别功能失败。

每阶段报告包含：执行环境、任务编号、实际命令、通过/失败数量、真实模型或替身的使用范围、必要的截图/SQL 结果和未验证项。接口测试不能证明识别准确，模型测试不能证明权限安全，电脑浏览器测试不能证明手机可用。

## 12 进入实现前的顺序

1. 审阅本计划，确认以本地单人开发为当前范围。
2. 收到进入实现的明确指令后，从 P1-01 开始，先完成 P1 门槛。
3. P2 尽早验证模型安装和运行风险；照片不足时继续独立的基础任务并保留未通过项。
4. 按 P3 → P4 → P5 推进可演示功能，阶段内同步完成接口、页面与对应测试。
5. P6 验证稳定性和手机操作，最后再制定与执行云部署计划。
